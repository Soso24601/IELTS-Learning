# 完整音轨并行识别实验

目标：用户仍一次取得整段视频的完整英文字幕和时间轴，验证服务器内部并行处理是否比整条识别更快。实验不会解决 YouTube 获取音轨受限，也不会降低当前浏览器暂存完整音轨的开销。

## 操作

在字幕面板的“完整字幕识别方式”中选择：

- 整条识别：原有方式。
- 并行识别完整音轨（实验）：约每 10 分钟一段，最多 3 段同时识别，全部成功后合并。
- 对比两种方式耗时：同一音轨先整条识别，再运行并行流程。会识别两次并按百炼实际用量计费；对比本身会比单次识别等待更久。中文翻译只在最后执行一次。

随后使用“本机快速提取音轨并识别”，或上传已有音频。结果保存后，视频下方的“完整字幕处理耗时”会保留本机获取、上传、整条识别、切分、并行识别及翻译耗时。并行流程总时间包含切分时间，不能只比较最后一段返回的时刻。

## 实现与限制

- FFmpeg 仅处理上传到服务器的本地临时文件。单次解码、选取第一个声道、16 kHz FLAC 输出，与识别接口 channel_id=[0] 一致；文件落盘，避免在内存中保存解码后的整条音轨。
- 使用分段清单中的真实起止时间恢复字幕时间轴；不把每段都从视频第 0 秒显示。
- 每个用户最多一个任务，全站最多两个上传/识别任务。每个并行任务最多三个百炼子任务，轮询间隔 5 秒。
- 任一分段失败后不再提交新的分段；等待已经提交的工作结束后再清理临时文件。不会把部分字幕作为成功结果。对比模式若并行失败，会保留已成功的整条结果并说明原因。
- 音频样本完整不代表识别文字绝对一致：切分边界可能影响断词和上下文。对比时应检查交界前后句子、末尾是否完整和高亮时间轴。
- 任务当前存在服务器内存中，服务重启会丢失进行中的任务。实测时不要重新部署；结果完成后保存到原材料。
- 默认仍为整条识别。未获得同一真实音轨的完整对比报告前，不宣称并行方案已提速。

## 验证

`npm test` 覆盖并发上限、乱序完成后的合并、失败不交付残缺结果、静音片段、时间戳范围、百炼请求格式和截止时间。

`tools/verify-audio-split.ts` 使用真实 FFmpeg 生成 21 秒音频并切成 5 段，对比切分前后全部 PCM 样本，验证无丢失、无重复。此测试只证明切分正确，不代表百炼真实识别速度。

本地完整 Docker 构建遇到 Docker Hub 网络错误时，可在已有 Alpine/Node 隔离容器安装官方 ffmpeg 包运行上述验证；生产依赖已加入 Dockerfile，仍须检查 Zeabur 构建成功。
